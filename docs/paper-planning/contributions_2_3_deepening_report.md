# 后两个创新点深化汇报

## 1. 汇报主线

本项目在完成 EKF 单 Kernel 融合之后，继续围绕后两个创新点展开深化：

| 创新点 | 原始方案 | 深化目标 | 最终判断 |
|---|---|---|---|
| 混合精度优化 | 全局 fp32 | 区分 I/O、计算、矩阵乘法的精度需求 | 推荐 `fp16 I/O + fp32 计算 + ieee matmul` |
| Batch 并发优化 | `grid=(B,)` 多轨迹并行 | 分析不同 batch size 下的资源竞争和吞吐上限 | 推荐 `B = SM 数量`，Hopper 上为 `B=78` |

核心观点：

> EKF 这类负载不是传统大矩阵计算，而是高频、长序列、小矩阵、强递推依赖的状态估计任务。因此优化不能简单套用深度学习 GPU 经验，而要根据算法结构选择合适的精度和并发方式。

---

## 2. 创新点二：混合精度优化深化

### 2.1 问题背景

原始 EKF 使用 fp64 计算，精度高但速度慢。实验表明，降到 fp32 后仍能保持定位精度，同时吞吐大幅提升。

进一步的问题是：

- 是否还能继续降低数据精度？
- Tensor Core / TF32 是否能继续加速？
- 哪些部分可以降精度，哪些部分必须保留 fp32？

### 2.2 分层精度设计

我们没有采用“全部降精度”的做法，而是把 EKF 计算拆成三类：

| 层级 | 内容 | 可选精度 | 作用 |
|---|---|---|---|
| I/O 精度 | IMU、里程计输入，位置/速度输出 | fp32 / fp16 / bf16 | 影响显存带宽和数据存储 |
| EKF 计算精度 | 状态递推、协方差更新、误差补偿 | fp32 | 保证数值稳定性 |
| 矩阵乘法精度 | Triton `tl.dot` 小矩阵乘法 | ieee / tf32 | 测试 Tensor Core 是否有效 |

测试方案包括：

| 方案 | I/O | EKF 计算 | 矩阵乘法 | 目的 |
|---|---|---|---|---|
| fp32-baseline | fp32 | fp32 | ieee | 基线 |
| fp16-io | fp16 | fp32 | ieee | 测试 I/O 降精度 |
| bf16-io | bf16 | fp32 | ieee | 测试 bf16 是否适合传感器数据 |
| tf32-dot | fp32 | fp32 | tf32 | 测试 Tensor Core 小矩阵收益 |
| bf16-io+tf32 | bf16 | fp32 | tf32 | 测试组合降精度 |

### 2.3 实验结论

| 方案 | 性能表现 | 精度表现 | 结论 |
|---|---|---|---|
| fp32-baseline | 约 243k steps/s | 亚毫米级 | 稳定基线 |
| fp16-io | 约 229k steps/s | 额外误差小于 0.5 mm | 可行 |
| bf16-io | 性能无优势 | Z 轴漂移明显 | 不推荐 |
| tf32-dot | 比 fp32 更慢 | 精度略有下降 | 不推荐 |
| bf16-io+tf32 | 更慢且漂移 | 综合最差 | 不推荐 |

关键原因：

- `fp16-io` 可行：传感器数据范围适合 fp16，计算时再提升到 fp32，精度损失很小。
- `bf16-io` 不可行：bf16 尾数只有 7 bit，难以保留毫米级差分，长序列积分后会造成明显漂移。
- `tf32-dot` 不适合：EKF 矩阵规模通常只有 15x15，padding 到 16x16 后仍然太小，Tensor Core 的额外开销超过计算收益。

### 2.4 可行方案

推荐方案：

```text
传感器 I/O: fp16
EKF 核心计算: fp32
矩阵乘法: ieee fp32
```

适用场景：

- 显存带宽或数据传输压力较大；
- 需要同时处理大量传感器轨迹；
- 希望在不牺牲定位精度的前提下降低存储和 I/O 开销。

不推荐方案：

- 不推荐 bf16 作为位置积分和里程计差分相关数据的存储精度；
- 不推荐对 15x15 级别小矩阵使用 TF32 / Tensor Core 作为主要优化手段。

## 3. 创新点三：Batch 并发优化深化

### 3.1 问题背景

EKF 的单条轨迹在时间维度上存在严格依赖：

```text
x(k) 依赖 x(k-1)
P(k) 依赖 P(k-1)
```

因此，单轨迹内部很难继续并行化。但在仿真、参数搜索和蒙特卡洛实验中，不同轨迹之间互不依赖，可以做轨迹级并行。

原始方案是：

```text
一个 CUDA block 处理一条完整轨迹
grid = (B,)
```

深化工作的目标是回答三个问题：

- B 取多大最合适？
- GPU 什么时候进入资源竞争？
- 多 Stream overlap 是否有额外收益？

### 3.2 Batch 扫描结果

| Batch 区间 | GPU 状态 | 性能特点 | 结论 |
|---|---|---|---|
| B <= 78 | 每个 SM 约 1 个 block | 吞吐近似线性增长，效率约 99% | 最推荐 |
| 96 <= B <= 256 | 每个 SM 多个 block | 寄存器资源开始竞争，效率下降 | 可用于更高总吞吐 |
| B >= 312 | 每个 SM 约 4 个 block | 接近寄存器饱和，继续增大 B 收益下降 | 极限吞吐上限 |
| B > 312 | wave 调度开销增加 | 吞吐可能下降 | 应避免 |

Hopper GPU 有 78 个 SM，因此 `B=78` 是一个非常干净的并发点：

```text
B=78 -> 每个 SM 处理一条轨迹 -> 近似完美线性加速
```

### 3.3 Stream Overlap 结果

实验测试了 1、2、4、8 个 CUDA Stream，但收益基本小于 1%。

原因是：

- 当前 workload 非常均匀，每条轨迹长度相同，执行同一个 kernel；
- 一个 mega-kernel launch 已经把所有 block 交给 GPU hardware scheduler；
- 多 stream 不能创造新的并行度，只是增加软件调度复杂度。

因此，多 Stream overlap 对当前任务没有实质收益。

### 3.4 可行方案

推荐方案一：稳定高效方案

```text
Batch size = SM 数量
Hopper 上 B = 78
默认 stream
每个 CUDA block 处理一条轨迹
```

优点：

- 解释清晰；
- 资源竞争小；
- 吞吐随 B 近似线性增长；
- 适合作为论文中的主要系统级优化方案。

推荐方案二：离线极限吞吐方案

```text
Batch size 约等于 312
即每个 SM 约 4 个 block
```

优点：

- 总吞吐最高，可达到约 46M steps/s；
- 适合大规模蒙特卡洛仿真和参数搜索。

限制：

- 寄存器资源接近饱和；
- 效率低于 B=78；
- 继续增加 B 可能导致吞吐下降。

## 4. 两个创新点的关系

| 维度 | 混合精度优化 | Batch 并发优化 |
|---|---|---|
| 优化对象 | 单轨迹执行效率 | 多轨迹总吞吐 |
| 主要瓶颈 | 数据精度、存储带宽、小矩阵计算 | SM 占用、寄存器资源竞争 |
| 最优策略 | fp16 I/O + fp32 计算 | B 取 SM 数量附近 |
| 不推荐方向 | bf16、TF32 小矩阵 | 多 Stream overlap、过大 B |

二者是正交关系：

```text
混合精度解决“每条轨迹怎么算得更合适”
Batch 并发解决“多条轨迹如何把 GPU 填满”
```

联合可行路线：

```text
fp16 I/O + fp32 EKF 计算 + B=78
```

如果追求离线大规模仿真吞吐：

```text
fp16 I/O + fp32 EKF 计算 + B=312
```

---

## 5. 汇报总结话术

后两个创新点可以概括为：一个解决单轨迹数值执行效率，一个解决多轨迹系统吞吐。

在混合精度方面，我们发现 EKF 不能简单套用深度学习中的低精度策略。由于它包含长序列积分、协方差递推和毫米级差分，核心计算必须保持 fp32；但传感器 I/O 可以使用 fp16 存储，从而降低带宽压力。bf16 因尾数位不足会导致位置积分漂移，TF32 则由于矩阵规模太小，Tensor Core 开销超过收益。因此，最佳方案是分层混合精度，而不是全局降精度。

在 Batch 并发方面，我们利用多条轨迹之间相互独立的特点，让每个 CUDA block 处理一条完整轨迹。实验表明，当 batch size 不超过 GPU 的 SM 数量时，吞吐几乎线性增长；超过 SM 数量后，寄存器竞争逐渐增强；到每个 SM 约 4 个 block 时接近饱和，再继续增加 batch size 会导致效率下降。多 Stream overlap 对这种均匀 mega-kernel 没有明显收益。因此，推荐使用 `B=SM 数量` 作为稳定高效方案，用 `B≈312` 作为离线极限吞吐方案。

整体来看，这两个深化点说明：本文的 GPU 优化不是简单堆硬件特性，而是围绕 EKF “长序列、小矩阵、强依赖”的结构特点，分别从数值精度和系统并发两个层面找到真正有效的优化路径。
